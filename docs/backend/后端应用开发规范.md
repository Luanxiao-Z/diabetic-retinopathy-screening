# 后端应用开发规范

## 1. 技术选型约束

- 后端应用使用 Spring Boot 进行开发。
- 后端应用使用 **MySQL 8.x** 进行数据存储，字符集统一 `utf8mb4`，排序规则统一 `utf8mb4_0900_ai_ci`（区分大小写的字段单独使用 `utf8mb4_0900_as_cs`）。
- 后端应用使用 MyBatis-Plus 进行数据库操作。
- 后端应用使用 Knife4j（Swagger）进行接口文档管理。
- 后端应用使用 Redis 进行缓存存储。
- 后端应用所有接口必须提供中文 Swagger 注解说明，包括接口说明、请求参数、响应参数、异常码。

## 2. RESTful 服务规范

### 2.1 核心原则

1. **路径即资源**：URL 路径中只允许出现**资源名词**，不得出现任何操作动词或 RPC 风格动作名。
2. **操作由 HTTP 方法表达**：同一资源路径通过不同 HTTP 方法区分增删改查。
3. **资源使用复数**：集合资源使用复数名词，单个资源用集合路径 + 标识符。
4. **小写与连字符**：路径全部小写，单词之间用连字符 `-` 分隔，禁止驼峰与下划线。
5. **层级表达从属**：从属资源用嵌套路径表达，如 `/users/{id}/permissions`。

**禁止的 RPC 风格写法**（必须改写）：

| 禁止写法（RPC 风格） | 正确写法（RESTful） |
| --- | --- |
| `POST /api/v1/admin/user/add` | `POST /api/v1/admin/users` |
| `POST /api/v1/admin/user/update` | `PUT /api/v1/admin/users/{id}` |
| `POST /api/v1/admin/user/delete` | `DELETE /api/v1/admin/users/{id}` |
| `POST /api/v1/admin/user/getList` | `GET /api/v1/admin/users` |
| `POST /api/v1/admin/user/getById` | `GET /api/v1/admin/users/{id}` |
| `POST /api/v1/biz/order/list` | `GET /api/v1/biz/orders` |
| `POST /api/v1/auth/login/password` | `POST /api/v1/auth/sessions` |
| `POST /api/v1/auth/logout` | `DELETE /api/v1/auth/sessions` |
| `POST /api/v1/common/dict/list` | `GET /api/v1/common/dicts/{domainCode}/items` |
| `POST /api/v1/open/user/sync` | `PUT /api/v1/open/users` |

### 2.2 URL 路径结构

```
/api/v1/{安全场景前缀}/{资源路径}
```

- 以 `/api` 开头，紧跟版本号 `v1`。
- **安全场景前缀**由权限控制规范统一分配，用于 Filter 链判定安全策略：`auth`、`common`、`admin`、`biz`、`open`、`config`。详见[后端API权限控制规范](../design/后端API权限控制规范.md)。
- **资源路径**为纯资源名词，不含任何动词。

### 2.3 HTTP 方法语义

| HTTP 方法 | 语义 | 幂等 | 典型路径 |
| --- | --- | --- | --- |
| `GET` | 查询资源（列表或详情），不产生副作用 | 是 | `GET /api/v1/admin/users`、`GET /api/v1/admin/users/{id}` |
| `POST` | 新增资源，或在集合上执行非幂等创建 | 否 | `POST /api/v1/admin/users` |
| `PUT` | 全量更新资源，或幂等的整体替换 | 是 | `PUT /api/v1/admin/users/{id}` |
| `PATCH` | 部分更新资源的某些属性 | 否 | `PATCH /api/v1/admin/users/{id}/state` |
| `DELETE` | 删除资源 | 是 | `DELETE /api/v1/admin/users/{id}` |

**方法选用规则**：

- 查询一律使用 `GET`，**禁止用 `POST` 承载查询**（原有"优先 POST"约定废止）。
- 完整替换用 `PUT`，仅修改少数字段用 `PATCH`。
- 删除用 `DELETE`；批量删除用 `DELETE` + 请求体携带 ID 数组。
- 对"状态变更"这类非 CRUD 操作，优先建模为资源的子资源或属性：`PATCH /users/{id}/state`，而非 `POST /users/disable`。
- 导出、统计等无法归入 CRUD 的操作，使用**名词化的子资源**：`GET /screening-records/statistics`、`GET /screening-records/exports`。

### 2.4 资源命名约定

| 场景 | 写法 | 示例 |
| --- | --- | --- |
| 集合资源 | 复数名词 | `/users`、`/screening-records` |
| 单个资源 | 集合 + 标识符 | `/users/{id}` |
| 从属资源 | 父资源 + 子资源 | `/roles/{id}/permissions` |
| 当前登录用户 | `me`（约定写法） | `/users/me/permissions` |
| 状态/属性变更 | 资源 + 属性名 | `/users/{id}/state` |
| 派生数据 | 资源 + 名词化子资源 | `/screening-records/statistics` |

标识符统一使用 `{id}` 占位，类型为字符串或长整型，与主键类型一致。

### 2.5 请求参数

| 参数形式 | 适用场景 | 注解 |
| --- | --- | --- |
| 路径参数 | 资源标识符 | `@PathVariable` |
| 查询参数 | `GET` 的过滤、分页、排序条件 | `@RequestParam` 或 DTO 对象绑定 |
| JSON 请求体 | `POST` / `PUT` / `PATCH` 的资源内容 | `@RequestBody` |
| 文件上传 | 二进制文件 | `MultipartFile` |

约定：

- **`GET` 请求一律使用查询参数，禁止携带请求体。**
- 查询条件较多时，用 DTO 对象接收查询参数（Spring 支持对象绑定），DTO 内字段使用小驼峰。
- 分页参数统一：`current`（当前页，从 1 开始）、`pageSize`（每页条数，默认 10，最大 100）。
- 排序参数统一：`sortField`（字段名，小驼峰）、`sortOrder`（`asc` / `desc`）。
- 时间参数统一 `yyyy-MM-dd HH:mm:ss`；仅日期用 `yyyy-MM-dd`。
- 所有入参对象必须做参数校验（`@Valid` + JSR-303 注解）。

### 2.6 请求头

| 请求头 | 必填 | 说明 |
| --- | --- | --- |
| `Content-Type` | 是 | 非文件请求为 `application/json;charset=UTF-8` |
| `X-Access-Token` | 条件必填 | 登录令牌，除匿名接口外必须携带 |
| `Accept-Language` | 否 | 国际化语言标识 |

### 2.7 时间格式约定

- 响应体时间字段统一序列化为 `yyyy-MM-dd HH:mm:ss`。
- 全局 Jackson 配置 `spring.jackson.time-zone=GMT+8`。
- 禁止返回时间戳数字或带时区偏移的 ISO-8601 字符串（对外集成接口除外，需单独声明）。

## 3. 响应体契约

### 3.1 统一响应结构

所有接口（含异常响应）必须返回统一结构：

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `code` | int | 是 | 业务结果码，见 3.3 |
| `msg` | String | 是 | 结果描述，面向调用方的中文提示 |
| `data` | T | 否 | 业务数据，失败时可省略 |

### 3.2 HTTP 状态码规范

**业务异常维持 HTTP 200**，业务结果完全由响应体 `code` 表达；仅 `401` / `403` 同时返回对应的 HTTP 状态码。

| 操作 / 场景 | HTTP 状态码 | 响应体 `code` | 说明 |
| --- | --- | --- | --- |
| 任意成功响应（含 `POST` 新增、`DELETE` 删除） | `200` | `200` | 含 `data` 或仅 `code`/`msg` |
| 参数错误 / 业务校验失败 | `200` | `400` | 含 `msg` |
| 系统内部错误 | `200` | `500` | 含 `msg` |
| 注册限流 | `200` | `429` | 含 `msg`；注册为「IP + 全站」双层 |
| 登录防爆破 | `200` | `429` | 含 `msg`；同一 IP 5 分钟内累计 10 次失败触发，成功登录清零 |
| 模型服务不可用 | `200` | `503` | 含 `msg` |
| 未登录 / 令牌失效 | `401` | `401` | 含 `msg` |
| 无权限 | `403` | `403` | 含 `msg` |
| 静态资源不存在 | `404` | `404` | `NoResourceFoundException` 由全局处理器写入 |

**说明**：

- 不使用 `201 Created` 与 `204 No Content`，所有业务响应均为 HTTP 200 + 统一响应体，便于前端拦截器统一解析。
- `GlobalExceptionHandler` 统一捕获 `BusinessException`、参数校验异常与 `UnauthorizedException` / `AccessDeniedException`，按上表写出 HTTP 状态与信封码。规则见[后端API权限控制规范](../design/后端API权限控制规范.md)。

### 3.3 业务结果码（code）规范

| code | 含义 | 典型场景 |
| --- | --- | --- |
| `200` | 成功 | 业务正常处理完成 |
| `400` | 请求参数错误 / 业务校验失败 | 参数缺失、格式错误、业务规则不满足 |
| `401` | 未登录或登录已过期 | 令牌缺失、失效 |
| `403` | 无权限访问 | 功能权限或数据权限不足 |
| `404` | 资源不存在 | 静态资源或路由不存在 |
| `429` | 请求过于频繁 | 注册限流（IP + 全站双层）、登录防爆破（同 IP 失败计数） |
| `500` | 系统内部错误 | 未捕获异常 |
| `503` | 依赖服务不可用 | 数据库、Redis、对象存储、外部模型服务不可用 |

> 结果码定义见 `drs-module-common` 的 `ApiCode` 枚举；超出枚举范围的码由 `Result.fail(code, msg)` 直接构造。

**判定原则**：

- `code` 由服务端权威判定，前端不得自行推断。
- 批量处理场景：逐项独立处理，单张失败不影响其它影像，失败项在 `data` 中逐条反馈（如筛查上传）。
- 分页查询无数据属于成功，`code` 返回 `200`，`data.list` 为空数组。

### 3.4 响应示例

- 普通成功响应（`DELETE /api/v1/admin/users/{id}`，HTTP 200）

```json
{
  "code": 200,
  "msg": "success"
}
```

- 查询单个资源（`GET /api/v1/admin/users/{id}`，HTTP 200）

```json
{
  "code": 200,
  "msg": "success",
  "data": {
    "id": "3f2a1b9c7d5e4f6a8b0c1d2e3f4a5b6c",
    "username": "zhangsan",
    "realName": "张三",
    "role": "DOCTOR",
    "phone": "13800000000",
    "status": "ENABLED",
    "createTime": "2026-10-28 14:30:00"
  }
}
```

- 分页查询（`GET /api/v1/admin/users?current=1&pageSize=10`，HTTP 200）

```json
{
  "code": 200,
  "msg": "success",
  "data": {
    "total": 100,
    "list": [],
    "current": 1,
    "pageSize": 10
  }
}
```

- 业务校验失败（参数错误，HTTP 200 + 信封 `code=400`）

```json
{
  "code": 400,
  "msg": "手机号格式不正确"
}
```

- 未登录（HTTP 401）

```json
{
  "code": 401,
  "msg": "未登录或登录已过期"
}
```

> `msg` 为面向调用方的中文提示；成功时后端固定返回 `success`。分页参数名为 `current` / `pageSize`，不使用 `pageNum`。


## 4. 分层与编码规范

- 分层结构：`Controller` → `Service` → `Mapper`，禁止跨层调用。分层目录见[后端应用目录规划](后端应用目录规划.md)。
- Controller 只做参数接收与结果封装，不得编写业务逻辑。
- 数据库实体对象不得直接作为响应体返回，需转换为 VO/DTO。
- 统一使用构造器注入（`@RequiredArgsConstructor`），禁止字段注入 `@Autowired`。
- 事务注解 `@Transactional` 标注在 Service 方法上，`rollbackFor = Exception.class`。
- 日志使用 SLF4J，禁止使用 `System.out.println`。
- 包名全小写，按模块分层：`cn.edu.fzu.drs.模块.{controller|service|mapper|entity|dto|vo}`。

## 5. 数据库访问规范（MySQL）

- 统一使用 MyBatis-Plus，单表简单查询用 `LambdaQueryWrapper`，复杂查询写 XML。
- 主键由应用层生成 32 位无分隔符 UUID，字段类型 `CHAR(32)` / `VARCHAR(32)`。
- `update_time` 使用 MySQL 原生 `ON UPDATE CURRENT_TIMESTAMP` 自动维护，见[数据库设计规范](../design/数据库设计规范.md)。
- 禁止在 SQL 中拼接用户输入，一律使用参数绑定（`#{}`）。
- 禁止 `SELECT *`，必须显式列出字段。
- 禁止在循环中执行单条 SQL，改为批量操作。
- 大表分页查询禁止使用深度 `OFFSET`，改用游标或延迟关联。

## 6. 异常处理

- 全局异常处理使用 `@RestControllerAdvice`，统一转换为 3.1 的响应结构，并设置对应 HTTP 状态码。
- 业务异常使用自定义 `BizException`，携带 `code` 与 `msg`。
- 禁止在 Controller 内 `try-catch` 后吞掉异常。
- 系统异常必须记录完整堆栈日志；参数校验类异常记录 warn 级别日志即可。
- 异常信息不得包含 SQL、堆栈、内网地址等敏感内容。
