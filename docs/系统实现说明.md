## 一、系统定位

糖尿病视网膜病变（DR）智能筛查系统，面向基层医疗与眼科筛查场景，提供「上传眼底图 →
AI 五级分级 → 可解释热力图 → 转诊建议 → 记录管理 / 人工复核 / 患者随访 / 统计报表」的完整闭环。
本系统为医学人工智能课程项目，AI 结果仅供临床参考。

## 二、运行架构

系统由三个独立进程与三项基础设施构成，均为**本地运行**（容器化配置见 `deploy/`）：

| 组件 | 端口 | 职责 |
| --- | --- | --- |
| 前端 Web（Vue3 + Vite） | 5173 | PC 端业务界面；`/api` 代理至后端 |
| 后端（Spring Boot 3.4 / Java 21） | 8080 | 业务接口、权限与数据权限、对象存储、Excel 导出 |
| 模型服务（FastAPI + PyTorch） | 8000 | DR 五级推理与 Grad-CAM 热力图 |
| MySQL 8 | 3306 | 业务库 `dr_screening` |
| Redis 7 | 6379 | 令牌会话缓存 |
| MinIO | 9000 / 9001 | 眼底图与热力图私有桶 `dr-screening` |

### 交互约定

- **响应体**：统一 `{ code, msg, data }`；成功 `code=200`；业务异常保持 HTTP 200 + 信封 code；
  401/403 同时返回对应 HTTP 状态码
- **认证**：UUID 令牌 + Redis 会话（非 JWT），请求头 `X-Access-Token`
- **对象访问**：影像存于私有桶，前端使用 30 分钟有效期的预签名 URL
- **降级**：模型服务不可达时后端返回 `code=503`（「无法连接模型推理服务」），不影响已落库记录

## 三、后端模块划分

Maven 聚合工程，依赖方向为 `app → module-*`，模块之间单向依赖 `common`、`security`：

| 模块 | 内容 |
| --- | --- |
| `drs-module-common` | 统一响应 `Result` / `PageResult`、`BusinessException` 体系、`IdGenerator`、`PasswordUtil`（SHA-256 加盐）、权限常量、**审计契约 `OperationLogRecorder`** |
| `drs-module-security` | `AuthContext` / `AuthPrincipal`、`@RequirePermission` 注解与拦截、`PermissionResolver`（角色→权限映射与数据权限）、`DataScopeUtils` |
| `drs-module-system` | 认证（登录/登出）、当前用户、用户管理、字典管理、**操作日志（实现审计契约）** |
| `drs-module-screening` | 筛查上传与推理、记录分页/详情/删除、人工复核、统计、Excel 导出、患者随访聚合、模型信息代理 |
| `drs-app/drs-app-server` | 启动模块与 `GlobalExceptionHandler` |

### 关键设计决策

1. **审计契约下沉**：`drs-module-screening` **不依赖** `drs-module-system`，因此审计记录接口
   `OperationLogRecorder` 定义在 `common`，实现位于 `system`，运行期由 Spring 注入，
   避免为记录日志引入反向依赖。
2. **数据权限在服务层拼接**：`applyDataScope()` 依据登录主体的 `dataScope` 追加 `user_id` 过滤
   （SELF）或不限制（ALL），列表、详情、删除、导出、复核均复用该逻辑。
3. **实体为手写访问器**：工程**未启用** MyBatis-Plus 的 `MetaObjectHandler`，新建实体插入时
   必须显式设置 `id`（`IdGenerator.nextId()`）、`deleteFlag="N"` 与时间戳。
4. **名称映射空安全**：`Map.of(...)` 生成的不可变 Map 在 `get(null)` 时抛 NPE，
   故名称映射查询统一经 `BizScreeningRecordConvert.nameOf(names, key)`。
5. **异常处理完备**：`GlobalExceptionHandler` 覆盖业务异常、认证/权限、**参数校验（400，带字段提示）**、
   **路由不存在（404）** 与兜底 500。

## 四、数据模型

| 表 | 说明 |
| --- | --- |
| `sys_user` | 用户（用户名、姓名、角色、手机号、状态、密码摘要、审计字段） |
| `sys_dict_domain` / `sys_dict_item` | 字典域与字典项（编码为字符型） |
| `biz_screening_record` | 筛查记录：患者信息、影像与热力图对象键、分级、置信度、各分级概率（JSON）、转诊建议、模型版本、**人工复核字段**、审计字段 |
| `sys_operation_log` | 操作审计：操作人、模块、动作、对象、结果、失败原因、IP、耗时 |

初始化脚本 `sql/init/01_init_dr_screening.sql` **幂等**：建表使用 `IF NOT EXISTS`，
字典使用 `ON DUPLICATE KEY UPDATE`，字段变更使用基于 `information_schema` 的增量迁移判断。

> 执行注意：Windows 下 mysql 客户端需加 `--default-character-set=utf8mb4`，否则中文写入报 `ERROR 1366`。

## 五、核心业务流程

### 5.1 筛查上传（逐张独立）

前端选择图片后**先入队预览**（缩略图可点击放大确认），用户点击「开始筛查」后按**串行队列**
逐张提交，每张独立调用
`POST /biz/screening-records`（单文件 multipart）。后端对每张依次执行：

```
校验文件 → 上传 MinIO（fundus/yyyy/MM/dd/{id}.{ext}）
        → 调模型服务 /predict 获取分级与概率
        → 调模型服务 /cam 生成热力图并上传 MinIO（cam/...）
        → 落库（含置信度、概率 JSON、模型版本）
```

热力图生成失败**不阻断主流程**，仅记录告警，记录仍落库。
前端队列展示每张的状态与耗时，失败项可单独重试。

### 5.2 低置信度人工复核（闭环）

- 阈值常量：`BizScreeningRecordConvert.REVIEW_CONFIDENCE_THRESHOLD = 0.70`
- 置信度低于阈值（或缺失）→ `needReview=true`，未确认前计入「待复核」统计
- `PATCH /biz/screening-records/{id}/review` 记录复核人、时间与意见；
  重复复核返回 400；已确认的记录**不再计入待复核**
- 复核动作写入操作日志（模块 `SCREENING`，动作 `REVIEW`）

### 5.3 患者随访

`GET /biz/screening-records/patients` 按患者姓名归并历次筛查（仅统计已填姓名的记录），
计算最近/上次分级与变化方向：

| 方向 | 含义 |
| --- | --- |
| `UP` | 分级升高（进展） |
| `DOWN` | 分级降低（好转） |
| `SAME` | 与上次持平 |
| `FIRST` | 仅一次筛查 |

前端提供随访列表与时间线抽屉（时间线通过 `exactPatientName` 精确匹配查询）。

### 5.4 统计与环比

`GET /biz/screening-records/statistics` 返回分级分布、转诊建议分布、转诊率、
近 30 天逐日趋势，以及**环比**（近 30 天 vs 前 30 天数量与增长率）。
环比与列表筛选共用同一套过滤条件（`applyFilters`），保证口径一致。

### 5.5 诊断报告

前端独立页面（壳层内），A4 版式，含受检者信息、原图与热力图、分级结论与各分级概率表、
医师复核信息与免责声明；通过 `@media print` 支持打印或另存为 PDF。

## 七、模型服务

| 接口 | 说明 |
| --- | --- |
| `GET /health` | 健康检查：设备、CUDA 可用性、是否已加载训练权重 |
| `GET /model/info` | 模型元信息 + 训练指标（读取 `models/train_metrics.json`） |
| `POST /predict` | 多分类推理：分级编码、标签、置信度、各分级概率、转诊建议 |
| `POST /cam` | Grad-CAM 热力图（PNG），响应头返回 `X-Record-Id` / `X-Target-Level` / `X-Confidence` |

- 骨干 MobileNetV3-Small（5 类头），Grad-CAM 为**自实现**（numpy + PIL，不依赖 opencv / pytorch-grad-cam）
- 权重 `models/best_model.pth` 缺失时回退随机初始化（`/health` 的 `trained=false`），仅用于链路验证
- 训练入口 `training/train.py`：分层抽样 8:1:1、类别加权交叉熵、AdamW + CosineAnnealingLR、
  按验证集宏平均 F1 选优保存

## 八、已知限制与后续方向

| 类别 | 说明 |
| --- | --- |
| 模型精度 | 重度（LEVEL_3）测试样本仅 20 张，逐类 F1 波动较大；提升方向为数据规模、数据增强与类别重采样，而非增加训练轮次（最佳验证轮次出现在第 29 轮） |
| 单元测试 | 后端尚无自动化单测，关键业务逻辑依赖联调脚本覆盖 |
| 影像与演示数据 | 演示数据脚本生成的记录无真实影像（写入占位对象键），需要影像演示时请使用「演示样例」按钮或手工上传 |
| 对象存储清理 | 删除记录时会清理 MinIO 对象；异常场景下的残留对象需人工巡检 |
| 部署 | 提供容器化示例配置，尚未在容器环境中做完整端到端验证 |
