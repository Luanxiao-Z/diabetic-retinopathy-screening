# 数据字典规范

## 一、概述

### 1.1 规范目的

本规范旨在统一平台数据字典的定义、分类、编码和使用方式，确保各微服务、各数据模型在字典设计上保持一致性和可维护性。

> **相关规范**：数据库表/字段命名、类型选择等底层规范见 [数据库设计规范](./数据库设计规范.md)；PDManer 数据模型工具使用见 [数据模型规范](./数据模型规范.md)。

### 1.2 适用范围

- 平台所有后端微服务的数据模型设计
- 平台所有前端应用的数据展示与交互
- 数据库表结构设计中的数据字典字段定义

### 1.3 术语定义

| 术语 | 英文 | 说明 |
|------|------|------|
| 字典域 | Domain | 字典的分类容器，定义一组相关字典项的集合，如「订单状态」是一个字典域 |
| 字典项 | Item | 字典域下的具体条目，如「已支付」是「订单状态」字典域的一个字典项 |
| 主编码 | Domain Code | 字典域的唯一编码标识，如 `B_ORDER_STATUS` |
| 明细编码 | Item Code | 字典项的唯一编码标识，如 `1`（已支付） |
| 分类前缀 | Category Prefix | 主编码的前缀，标识字典的分类归属，如 `C_`、`S_`、`B_` |
| 树形字典 | Tree Dict | 具有父子层级关系的字典，通过 `parent_code` 字段构建 |

## 二、字典分类体系

### 2.1 三级分类架构

所有字典按以下三级分类组织，通过主编码前缀区分（以下为设计建议，非强制约束）：

| 分类 | 前缀 | 全称 | 定位 | 典型示例 |
|------|------|------|------|----------|
| **公用类** | `C_` | Common | 跨业务、跨系统的通用基础字典，任何模块均可直接引用 | `C_STATUS`（记录状态）、`C_YES_NO`（是否）、`C_DELETE_FLAG`（删除标记） |
| **系统类** | `S_` | System | 技术/平台级定义，描述系统运行所需的基础设施类字典 | `S_APP_TYPE`（应用端类型）、`S_LOG_LEVEL`（日志级别）、`S_DATA_SOURCE`（数据源类型）、`S_API_TYPE`（接口类型） |
| **业务类** | `B_` | Business | 具体业务领域的定义，按业务模块进一步划分子前缀 | `B_CERT_TYPE`（证件分类）、`B_ORDER_STATUS`（订单状态）、`B_GENDER`（性别）、`B_PAY_TYPE`（支付方式） |

### 2.2 分类判别标准

当不确定字典应归属哪个分类时，按以下决策树判断：

```
该字典是否为跨所有业务领域的通用概念？
  ├── 是 → 公用类 (C_)
  └── 否 → 该字典是否属于技术/平台基础设施，与具体业务无关？
              ├── 是 → 系统类 (S_)
              └── 否 → 业务类 (B_)
```

**判别要点：**

| 分类 | 关键特征 |
|------|----------|
| 公用类 | 所有模块都能直接使用，无业务边界限制；通常只有一项固定语义；如：是否、有效状态 |
| 系统类 | 描述系统运行机制，而非业务规则；通常由基础设施/平台团队统一维护 |
| 业务类 | 有明确的业务领域归属；由对应业务模块的团队维护 |

### 2.3 业务类子前缀（可选扩展）

业务类字典数量较多时，可在 `B_` 后增加业务模块缩写，便于分类管理：

| 子前缀 | 业务模块 | 示例 |
|--------|----------|------|
| `B_ORDER_` | 订单模块 | `B_ORDER_STATUS`、`B_ORDER_TYPE` |
| `B_USER_` | 用户模块 | `B_USER_CERT_TYPE` |
| `B_PRODUCT_` | 商品模块 | `B_PRODUCT_CATEGORY`、`B_PRODUCT_UNIT` |
| `B_PAY_` | 支付模块 | `B_PAY_TYPE`、`B_PAY_CHANNEL` |

> **注意**：子前缀为可选，仅在业务模块较多时使用。简单业务可直接用 `B_XXX` 命名。

## 三、编码规范

### 3.1 主编码（domain_code）规范

主编码是字典域的唯一标识，采用**字符型**编码。

| 规则项 | 规范要求 | 正确示例 | 错误示例 |
|--------|----------|----------|----------|
| 字符集 | 大写英文字母 + 下划线 | `C_STATUS`、`B_ORDER_STATUS` | `c_status`、`OrderStatus` |
| 前缀 | 建议使用分类前缀 `C_` / `S_` / `B_` | `B_CERT_TYPE` | `CERT_TYPE`（缺少前缀） |
| 命名风格 | 单词间用单下划线分隔，语义清晰 | `S_APP_TYPE` | `S_APPTYPE`、`S_AT` |
| 长度限制 | 不超过 50 个字符 | — | — |
| 唯一性 | 全局唯一，不得重复 | — | — |
| 禁止字符 | 禁止使用数字开头、特殊符号 | `B_ORDER_STATUS` | `B_1ST_STATUS` |

### 3.2 明细编码（item_code）规范

明细编码是字典项的唯一标识。

#### 3.2.1 数值型编码（优先推荐）

| 规则项 | 规范要求 | 示例 |
|--------|----------|------|
| 编码范围 | 建议从 1 开始递增 | `1`, `2`, `3`, ... |
| 编码长度 | 整型采用1~3位数字, 如: 1~999, 适用于高性能且明细编码较少的业务场景 |
| 0 值建议 | **二值判断场景建议 0=否定/1=肯定**，多值等场景允许灵活使用 0 | 见下方说明 |
| 间距 | 相邻项编码可留间隔（如 10, 20），便于后续插入 | `10`, `20`, `30` |
| 数据类型 | 数据库存储为 VARCHAR，但内容为数字字符串 | `'1'`, `'2'`, `'10'` |

**0 值使用建议：**

```
建议：  
0 = 否定含义（无效、否、不通过等）  
1 = 肯定含义（有效、是、通过等）  

允许的例外场景：
  - is_deleted / delete_flag 等基础设施字段：0=未删除/1=已删除（0为正常态，非否定语义）
  - 多值枚举（如性别 B_GENDER）：0=未知, 1=男, 2=女（0仅表示默认/未知，非否定）
  - 对接外部接口的编码：以外系统定义的编码为准，不强求从1开始
  - 其他业务需要自然使用 0 值的场景

核心原则：以上为设计时的推荐惯例，非强制约束。业务清晰时优先从1起编，
有合理需要时允许从0开始。关键在于域内风格统一、语义明确。
```

#### 3.2.2 字符型编码（特定场景使用）

字符型明细编码按业务场景分为三类适用方式，按以下场景判定选用风格：

##### 场景一：无语义化场景 → 优先采用数字字符串风格

适用于明细编码无需承载业务语义、仅作标识使用的场景（如业务变更频繁、明细无天然英文语义、团队偏好数字编码等）。此类场景**优先采用数字字符串风格**，编码为纯数字字符。

| 规则项 | 规范要求 | 示例 |
|--------|----------|------|
| 字符集 | 纯数字字符 `0-9` | `1`、`01`、`99`、`999` |
| 编码位数 | **允许 1 位、2 位、3 位等不同位数在同一字典域内混用**，不强制定长 | `1`、`10`、`99`、`999` |
| 起始编码 | 建议从 `1` 或 `01` 开始顺序编码 | `1`、`2`、`3` 或 `01`、`02`、`03` |
| 兜底编码 | 建议固定使用 `99` 表示"其他"；若域内采用 3 位编码体系，兜底可用 `999` | `99`、`999` |
| 预留扩展 | 相邻项可留间隔，便于后续插入 | `1`、`10`、`20`、`99` |
| 示例 | 订单状态 / 业务类型 | `01`（待支付）、`02`（已支付）、`10`（墓位业务）、`99`（其他） |

##### 场景二：需要语义化场景 → 采用英文语义字符风格

适用于编码本身需要承载业务语义、便于跨系统识别或代码可读性的场景（如编码即业务缩写、状态机状态标识等）。此类场景**采用英文语义字符风格**，编码为大写英文字母（含下划线）。

| 规则项 | 规范要求 | 示例 |
|--------|----------|------|
| 字符集 | 大写英文字母 + 下划线 | `ALIPAY`、`PENDING` |
| 语义 | 编码需具备明确业务含义，禁止无意义占位 | `WECHAT`（禁止 `TYPE_A`） |
| 命名风格 | 单词间用单下划线分隔，语义清晰 | `BANK_TRANSFER` |
| 示例 | 支付方式 / 状态机状态 | `ALIPAY`（支付宝）、`PENDING`（待支付）、`APPROVED`（已审批） |

##### 场景三：对标外部标准场景 → 参照外部标准定义

适用于需要与行业标准、国家标准、国际标准对接的场景（如 ISO 国家代码、行业分类代码等）。此类场景**允许参照外部标准定义字符型编码**，编码形式以外部标准为准（可能含字母、数字或其组合）。

| 规则项 | 规范要求 | 示例 |
|--------|----------|------|
| 编码来源 | 以外部标准（行业/国家/国际标准）定义为准 | ISO 3166 国家代码 |
| 字符集 | 按外部标准规定，可含字母、数字或其组合 | `CN`、`US`、`440` |
| 语义 | 与外部标准保持一致，不得自行改写 | `CN`（中国）、`US`（美国） |
| 示例 | 国家代码 / 行业分类 | `CN`、`US`、`JP` |

##### 通用规则

无论采用上述哪种风格，均须遵循以下通用约束：

| 规则项 | 规范要求 | 正确示例 | 错误示例 |
|--------|----------|----------|----------|
| 风格统一 | 同一字典域内只能选用一种风格，禁止同域混用 | — | 同域内同时出现 `PENDING` 与 `01` |
| 字符集 | 大写英文字母、数字、下划线的任意组合，允许字母与数字混用 | `01`、`ALIPAY`、`CN`、`A011`、`01A` | `AliPay`（小写）、`pending`（小写）、`01-A`（特殊符号） |
| 长度限制 | 不超过 50 个字符 | — | — |
| 数据类型 | 数据库存储为 VARCHAR，内容为字符型 | `'01'`、`'ALIPAY'`、`'CN'`、`'A011'`、`'01A'` | — |

> **数字字符串风格 vs 3.2.1 数值型编码的区别**：两者均以数字为内容，但本质不同——数字字符串风格属于字符型编码，存储类型为 VARCHAR，按字符串语义比较；数值型编码以整型语义优先（`1`、`2`、`10`），适合高性能、明细少的场景。无语义化场景下，若性能敏感优先用 3.2.1 数值型，若不敏感或业务偏好数字编码可采用本节数字字符串风格。

#### 3.2.3 编码类型选择决策树

```
字典项是否需要对标外部标准（行业/国家/国际标准）？
  ├── 是 → 使用字符型（参照外部标准），如 CN / US
  └── 否 → 字典项是否需要语义化（编码即业务标识/状态标识）？
              ├── 是 → 使用字符型（英文语义字符），如 PENDING / APPROVED
              └── 否 → 无语义化场景，按性能敏感度选择：
                      ├── 性能敏感 → 使用数值型（推荐），从 1 开始
                      └── 性能不敏感/业务偏好数字编码 → 使用字符型（数字字符串），如 01 / 02 / 99
```

#### 3.2.4 编码一致性约束

| 约束 | 说明 |
|------|------|
| 域内风格统一 | 同一个字典域（domain_code）内，所有 item_code 必须统一为同一种风格（全数值型、全数字字符串、全英文语义字符或全外部标准参照），**禁止风格类型混用**（如数字字符串 `01` 与英文语义字符 `PENDING` 不得同域共存） |
| 位数不强制统一 | 同一字典域内**允许不同位数的编码共存**（如 `1`、`10`、`99`、`999` 可同域存在），不强制定长，位数差异不视为风格混用 |
| 禁止类型混用 | 不允许同一字典域内同时出现数值型（3.2.1）与字符型（3.2.2）两种编码类型 |

### 3.3 多级字典编码规则

多级字典（树形结构）不使用层级拼接编码，采用 **item_code 平铺 + parent_code 关联** 的方式：

| 规则项 | 说明 |
|--------|------|
| item_code 平铺 | 所有层级 item_code 在同一命名空间内独立编号 |
| parent_code 关联 | 通过 `parent_code` 字段指向父级 item_code，顶层节点 `parent_code` 为 `NULL` |
| 不采用拼接 | **禁止**使用 `01-001-0001`、`01_001_0001` 等逐级拼接编码 |

**示例：商品分类（三级树形字典）**

```
B_PRODUCT_CATEGORY
├── item_code='1',  name='电子产品',   parent_code=NULL
│   ├── item_code='2',  name='手机',   parent_code='1'
│   │   ├── item_code='3',  name='智能手机', parent_code='2'
│   │   └── item_code='4',  name='功能手机', parent_code='2'
│   └── item_code='5',  name='电脑',   parent_code='1'
│       ├── item_code='6',  name='笔记本', parent_code='5'
│       └── item_code='7',  name='台式机', parent_code='5'
└── item_code='8',  name='服装',       parent_code=NULL
    ├── item_code='9',  name='男装',   parent_code='8'
    └── item_code='10', name='女装',   parent_code='8'
```

## 四、多级字典层级设计

### 4.1 树形结构设计

多级字典通过 `sys_dict_item` 表中的 `parent_code` 字段实现树形层级关系：

| 字段 | 值 | 含义 |
|------|-----|------|
| `parent_code` | `NULL` | 顶层（根）节点 |
| `parent_code` | 父级 item_code | 子节点，挂载到指定父节点 |

### 4.2 层级深度约束

| 约束 | 建议值 | 说明 |
|------|--------|------|
| 最大层级深度 | 5 级 | 过深的层级增加前端交互复杂度和查询性能开销 |
| 推荐层级深度 | 2-3 级 | 满足大部分业务场景（如：商品大类→商品小类） |

### 4.3 递归查询（MySQL 8 递归 CTE）

MySQL 8 支持 `WITH RECURSIVE` 递归 CTE，可直接查询完整树形结构。

```sql
-- 查询指定字典域下的完整树形结构
WITH RECURSIVE dict_tree AS (
    -- 根节点
    SELECT id, domain_code, item_code, item_name, parent_code, sort, 0 AS depth
    FROM sys_dict_item
    WHERE domain_code = 'B_PRODUCT_CATEGORY'
        AND parent_code IS NULL
        AND state = 1
    
    UNION ALL
    
    -- 递归子节点
    SELECT di.id, di.domain_code, di.item_code, di.item_name, 
           di.parent_code, di.sort, dt.depth + 1
    FROM sys_dict_item di
    INNER JOIN dict_tree dt ON di.parent_code = dt.item_code
    WHERE di.domain_code = 'B_PRODUCT_CATEGORY'
        AND di.state = 1
        AND dt.depth < 5
)
SELECT id, item_code, item_name, parent_code, sort, depth
FROM dict_tree
ORDER BY depth, sort;
```

### 4.4 前端展示建议

| 场景 | 推荐组件 | 说明 |
|------|----------|------|
| 2-3 级选择 | 级联选择器（Cascader） | 适合有限层级的分类选择 |
| 深层级选择 | 树形选择器（TreeSelect） | 支持搜索、展开/收起 |
| 平铺展示 | 分组下拉 + 面包屑导航 | 适合需要清晰导航的场景 |

## 五、数据模型设计

### 5.1 字典域表（sys_dict_domain）

```sql
CREATE TABLE sys_dict_domain (
    id              CHAR(32)       NOT NULL DEFAULT (REPLACE(UUID(), '-', '')) COMMENT '主键ID',
    domain_code     VARCHAR(50)    COLLATE utf8mb4_0900_as_cs NOT NULL COMMENT '字典域编码',
    domain_name     VARCHAR(100)   NOT NULL COMMENT '字典域名称',
    domain_desc     VARCHAR(500)   DEFAULT NULL COMMENT '字典域描述',
    sort            INT            NOT NULL DEFAULT 0 COMMENT '排序号',
    state           TINYINT        NOT NULL DEFAULT 1 COMMENT '记录状态(字典:C_STATUS)',
    state_time      DATETIME       NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '状态时间',
    create_by       CHAR(32)       DEFAULT NULL COMMENT '创建人ID',
    create_time     DATETIME       NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
    modify_by       CHAR(32)       DEFAULT NULL COMMENT '修改人ID',
    modify_time     DATETIME       NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '修改时间',
    PRIMARY KEY (id),
    UNIQUE KEY uk_dict_domain_code (domain_code)
) ENGINE = InnoDB
  DEFAULT CHARSET = utf8mb4
  COLLATE = utf8mb4_0900_ai_ci
  COMMENT = '字典域表';
```

- **字典域编码必须使用大写字母和下划线**，如 `C_STATUS`、`B_ORDER_STATUS`；分类前缀见[2.1 三级分类架构](#21-三级分类架构)
- **字典分类通过编码前缀区分**：`C_` 公用类，`S_` 系统类，`B_` 业务类
- **记录状态字段 `state` 取值**：0=失效，1=有效（字典域 `C_STATUS`）
- **字典表不使用逻辑删除字段**；废弃字典项通过 `state=0` 标记，不物理删除
- `domain_code` 使用 `utf8mb4_0900_as_cs` 排序规则，保证大小写敏感

### 5.2 字典明细表（sys_dict_item）

```sql
CREATE TABLE sys_dict_item (
    id              CHAR(32)       NOT NULL DEFAULT (REPLACE(UUID(), '-', '')) COMMENT '主键ID',
    domain_code     VARCHAR(50)    COLLATE utf8mb4_0900_as_cs NOT NULL COMMENT '字典域主编码',
    item_code       VARCHAR(50)    COLLATE utf8mb4_0900_as_cs NOT NULL COMMENT '字典明细编码',
    item_name       VARCHAR(100)   NOT NULL COMMENT '字典明细名称',
    item_desc       VARCHAR(500)   DEFAULT NULL COMMENT '字典明细描述',
    parent_code     VARCHAR(50)    COLLATE utf8mb4_0900_as_cs DEFAULT NULL COMMENT '父级字典明细编码',
    sort            INT            NOT NULL DEFAULT 0 COMMENT '排序号',
    state           TINYINT        NOT NULL DEFAULT 1 COMMENT '记录状态(字典:C_STATUS)',
    state_time      DATETIME       NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '状态时间',
    create_by       CHAR(32)       DEFAULT NULL COMMENT '创建人ID',
    create_time     DATETIME       NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
    modify_by       CHAR(32)       DEFAULT NULL COMMENT '修改人ID',
    modify_time     DATETIME       NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '修改时间',
    PRIMARY KEY (id),
    UNIQUE KEY uk_dict_item_code (domain_code, item_code),
    KEY idx_dict_item_domain (domain_code),
    KEY idx_dict_item_parent (domain_code, parent_code)
) ENGINE = InnoDB
  DEFAULT CHARSET = utf8mb4
  COLLATE = utf8mb4_0900_ai_ci
  COMMENT = '字典明细表';
```

- **字典项明细编码，优先正整数数值型，从1开始；0保留用于否定语义**
- **父级字典明细编码，用于构建树形字典，顶层节点为NULL**

### 5.3 表结构说明

| 表 | 核心字段 | 说明 |
|-----|----------|------|
| `sys_dict_item` | `item_code` | VARCHAR类型存储，数值型编码存数字字符串(`'1'`, `'2'`)，字符型编码存含义字符串(`'PENDING'`) |
| `sys_dict_item` | `parent_code` | 指向父级 item_code，构建树形层级。顶层节点为 NULL |

## 七、使用规范与最佳实践

### 7.1 业务表引用字典

业务表中涉及字典的字段，在字段注释中标注字典域编码：

```sql
-- 示例：订单表引用字典
CREATE TABLE biz_order (
    id              CHAR(32)       NOT NULL DEFAULT (REPLACE(UUID(), '-', '')) COMMENT '主键ID',
    order_no        VARCHAR(32)    NOT NULL COMMENT '订单编号',
    customer_id     CHAR(32)       NOT NULL COMMENT '客户ID',
    order_status    VARCHAR(20)    COLLATE utf8mb4_0900_as_cs NOT NULL COMMENT '订单状态(字典:B_ORDER_STATUS)',
    pay_type        VARCHAR(20)    COLLATE utf8mb4_0900_as_cs DEFAULT NULL COMMENT '支付方式(字典:B_PAY_TYPE)',
    cert_type       VARCHAR(20)    COLLATE utf8mb4_0900_as_cs NOT NULL COMMENT '证件类型(字典:B_CERT_TYPE)',
    is_deleted      TINYINT        NOT NULL DEFAULT 0 COMMENT '删除标记(字典:C_DELETE_FLAG)',
    state           TINYINT        NOT NULL DEFAULT 1 COMMENT '记录状态(字典:C_STATUS)',
    state_time      DATETIME       NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '状态时间',
    create_by       CHAR(32)       DEFAULT NULL COMMENT '创建人ID',
    create_time     DATETIME       NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
    modify_by       CHAR(32)       DEFAULT NULL COMMENT '修改人ID',
    modify_time     DATETIME       NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '修改时间',
    PRIMARY KEY (id)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4 COLLATE = utf8mb4_0900_ai_ci COMMENT = '业务订单表';
```

**标注格式：** `字段含义(字典:DOMAIN_CODE)`

### 7.2 字典关联查询

```sql
-- 单字典关联查询
SELECT 
    o.id,
    o.order_no,
    o.order_status,
    di.item_name AS order_status_name
FROM biz_order o
LEFT JOIN sys_dict_item di 
    ON di.domain_code = 'B_ORDER_STATUS' 
    AND di.item_code = o.order_status
    AND di.state = 1;

-- 多字典关联查询
SELECT 
    o.id,
    o.order_no,
    ds.item_name AS order_status_name,
    dp.item_name AS pay_type_name,
    dc.item_name AS cert_type_name
FROM biz_order o
LEFT JOIN sys_dict_item ds 
    ON ds.domain_code = 'B_ORDER_STATUS' AND ds.item_code = o.order_status
LEFT JOIN sys_dict_item dp 
    ON dp.domain_code = 'B_PAY_TYPE' AND dp.item_code = o.pay_type
LEFT JOIN sys_dict_item dc 
    ON dc.domain_code = 'B_CERT_TYPE' AND dc.item_code = o.cert_type
WHERE o.is_deleted = 0;
```

### 7.3 缓存策略

| 策略 | 说明 | 推荐场景 |
|------|------|----------|
| 应用启动加载 | 公用类字典启动时全量加载到内存 | `C_STATUS`、`C_YES_NO` |
| 定时刷新 | 系统类字典每 N 分钟从 DB 刷新 | `S_APP_TYPE`、`S_LOG_LEVEL` |
| 惰性加载 + TTL | 业务类字典首次访问时加载，设置过期时间 | `B_ORDER_STATUS`、`B_CERT_TYPE` |

**推荐缓存Key格式：** `dict:{domain_code}` → `List<DictItem>`

> 缓存中的 `domain_code` 必须与数据库保持完全相同的大小写（依赖 `utf8mb4_0900_as_cs` 排序规则保证区分）。

### 7.4 字典维护流程

#### 7.4.1 新增字典

1. 确认字典分类归属（C / S / B）
2. 按编码规范确定 domain_code
3. 在 `sys_dict_domain` 插入字典域记录
4. 在 `sys_dict_item` 插入各字典项记录
5. 建议预留编码间隔（如 item_code 按 10 递增），便于后续插入

#### 7.4.2 修改字典

| 操作 | 是否允许 | 说明 |
|------|----------|------|
| 修改 `item_name` | ✅ 允许 | 仅改名称，编码不变 |
| 修改 `item_code` | ❌ 禁止 | 编码一旦确定不得修改 |
| 修改 `domain_code` | ❌ 禁止 | 域编码一旦确定不得修改 |
| 删除字典项 | ❌ 不推荐 | 使用 `state=0` 标记失效，而非物理删除 |

#### 7.4.3 废弃字典项

当字典项不再使用时，不建议物理删除，而是将其 `state` 设为 `0`：

```sql
-- 废弃某字典项（标记为无效）
UPDATE sys_dict_item SET state = 0 WHERE item_code = 'REFUNDING' AND domain_code = 'B_ORDER_STATUS';
```

**废弃原则：**
- 历史数据仍需展示的字典项：仅标记 `state=0`，保留数据
- 从未被引用的字典项：可考虑物理删除（需确认无引用）

### 7.5 性能优化建议

| 场景 | 建议 |
|------|------|
| 高频查询 | 将公用类、系统类字典缓存到 Redis，减少 DB 查询 |
| 报表查询 | 可在业务表中冗余存储 `item_name`，避免大量 JOIN |
| 树形字典 | 递归查询只查有效项（`state=1`），限制深度 |
| 批量查询 | 按 domain_code 批量加载，避免 N+1 问题 |
